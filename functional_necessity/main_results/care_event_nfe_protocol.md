## 1. 推荐规则

### 1.1 候选与回退

- 候选 NFE = {1, 2, 3}；参考 NFE = 10；回退 NFE = 10。
- 按 1→2→3 依次检查，推荐**最低的通过者**。没有候选通过时回退 10。
- 允许全部拒绝；不强制输出任何已知 NFE。
- 若某候选缺少探针输出，标为“不可评估”并跳过，不算通过。
- 若较低候选通过而较高候选被拒，照常推荐较低者，并在输出里标出“非单调”。

### 1.2 每个观测上的量

对选中的每个观测 i，在噪声 j∈{0,1} 下，比较同一观测、同一初始噪声时 NFE=n 与 NFE=10 的输出。只取前 10 步，在策略归一化空间里计算。

| 量 | 定义 |
|---|---|
| 手臂误差 e_i(n) | 前 6 维（平移＋旋转）的 RMSE，**先在两种噪声间取平均**，每个观测得一个值 |
| 随机基准 f_i | NFE=10 的 noise0 与 noise1 输出之间的手臂 RMSE，即同一状态下模型自身的重采样差异 |
| 夹爪偏差 k_i(n) | 两种噪声中，出现任一步开合判定不一致的比例（0、0.5 或 1）。开合判定为反标准化后 g>0 |
| 夹爪基准 h_i | NFE=10 的 noise0 与 noise1 是否有任一步开合不一致（0 或 1） |
| 严重偏差 s_i(n)、hs_i | 同上，但只计不一致步数 ≥3 的情况 |

两种噪声始终绑定在同一观测内聚合，不当作独立样本。置信区间以 episode 为簇做 bootstrap（B=2000，种子 20261015）。

### 1.3 四项检查（全部通过才算该 NFE 通过）

| 检查 | 条件 | 数值 |
|---|---|---|
| 手臂中位 | median_i e_i(n) ≤ c_med · median_i f_i | c_med = 1.0 |
| 手臂尾部 | P95_i e_i(n) ≤ c_tail · P95_i f_i | c_tail = 1.0 |
| 夹爪比例 | mean_i k_i(n) − mean_i h_i ≤ m_g | m_g = 0 |
| 严重夹爪 | mean_i s_i(n) − mean_i hs_i ≤ m_s（严重 = 10 步中 ≥3 步） | m_s = 0 |

另有一条退化保护：若 median_i f_i < 1e-3（模型对噪声几乎确定），基准不可用，直接回退 10 并提交复核。

**数值依据**

1. **比值取 1.0。** f_i 是“把 NFE=10 的一次采样换成另一次独立采样”造成的动作差异。e ≤ f 的含义是：少步求解带来的偏移不超过模型自身重采样的差异。1.0 是“与重采样无法区分”这一解释的自然边界，不是在开发数据上搜出来的。基准按模型、按选中观测在同一次运行中计算，量纲自动抵消，所以不需要逐模型设定绝对阈值。Molmo 的 QUANTILES 归一化与 Pi/Smol 的 MEAN_STD 也因此不必换算。
2. **尾部取 P95，不用 max。** 每个策略只有 120 个观测，max 只由一个点决定。P95 约由第 6 大的值决定，既保留尾部信息，也不至于被单点主导。
3. **夹爪差额取 0。** 夹爪偏差率不得高于同一批状态上 NFE=10 自身的重采样不一致率。按每次比较计率，k 用 2 次比较，h 用 1 次比较，口径相同。
4. **严重阈值取 3 步。** 1–2 步的不一致对应开合时刻的轻微前后移动；≥3 步占执行块的 30%，按“开合决策改变”计。这是预先定义的严重程度，不随数据调整。
5. **点估计判定，区间只报告。** 置信区间不参与判定，避免在 n=120 时几乎总是拒绝。是否改用“上置信界 ≤ 1”属于冻结前要决定的事项（§8）。

### 1.4 为什么不沿用 P5/P95 尾部阈值

旧诊断里的 `cos<P5 or rmse>P95` 阈值，取自校准 480 帧上 NFE=1 自身的分布，所以按构造就会把约 5% 的点标为尾部。它适合比较“哪种选样抓到更多尾部”，不能判断 NFE=1 本身是否可接受，也不是质量保证。本协议只保留这类分位数作开发诊断，判定一律相对于同批状态上 NFE=10 的随机基准。

### 1.5 四种策略用同一条规则

Random、α、G-only、α_event 使用完全相同的候选集合、四项检查和数值，没有策略专属阈值。差别只在“用哪 120 个观测算这四项”。

结构上要注意：事件富集会同时抬高 e 和 f（例如 Pi 的夹爪基准从 Random 的 2/120 升到 G-only 的 8/120）。因此 CARE 选样**不会**按构造让规则变得更严。CARE 可能的价值在于揭示风险、节省探针预算，不在于改变推荐出的 NFE。

## 2. 筛查指标与独立验证质量条件

| | 筛查指标（推荐阶段） | 独立验证质量条件 |
|---|---|---|
| 样本 | 各策略选中的 120 个观测，事件富集 | 独立 episode 上的均匀抽样观测，不富集 |
| 用途 | 决定推荐哪个 NFE | 检验推荐是否成立 |
| 读法 | 富集状态下的压力测试率；**不能当作部署风险** | 总体层面的离线质量估计，带置信区间 |
| 聚合 | 观测级；两种噪声绑定 | 观测级；按 episode 聚簇 bootstrap |

**独立验证质量条件**（对每个策略的推荐 n*，与回退 10 比较）：

1. **离线质量。** 在验证集上用 §1.3 的同一组四项检查，以点估计判定，同时报告 95% 簇 bootstrap 区间。若 n* 在验证集上未通过，记为“误推荐”。若筛查阶段被拒的较低 NFE 在验证集上通过，记为“保守拒绝”，这是成本，不是错误。
2. **闭环质量。** 与同协议、同 n 的 NFE=10 相比，Avg 下降不超过 2.0 pp（沿用 `eval_nfe_libero.md` 的通过规则），且每个套件下降不超过 5 pp。5 pp 是对旧文“没有套件塌掉”的量化，约为 100 回合套件的 2.5 个二项标准误，**新增数值，需审批**。
3. 回退 10 不需要闭环比较。若不同策略给出相同的 n*，共用同一轮闭环，不能写成不同的“方法 SR”。

均匀验证集上的事件很少（草稿验证集 480 个观测中 G=1 只有 40 个），夹爪比例的区间会很宽。离线验证对夹爪的检验力有限，夹爪方面以闭环为主要质量条件。

## 4. 分阶段入口与预算

```text
freeze → split → select → probe-plan → [GPU 探针，仅跑并集] → probe-import → recommend
       → validation-plan → [GPU 探针，验证集] → validation-import → validate
dev：run-dev = freeze → select → seal-dev → recommend → validate
```

**写盘与锁定**

- 每个阶段把输出写到 `<run>/0x_*`，并在 `ledger.jsonl` 追加文件 sha256 和 UTC 时间。
- `freeze` 记录配置和 6 个代码文件的哈希；之后任何阶段发现配置或代码变化都会拒绝运行。
- `DRAFT` 运行不能冻结。`--draft` 只允许用于 split / select / probe-plan。

**隔离**

- `recommend` 只读 `03_probe/<model>/sealed_union.npz`，其中只有被选中观测的并集，并按各策略自己的索引截取。它不读未选中候选，也不读验证集。
- 验证探针的请求只能在推荐的 ledger 条目之后生成。`validate` 要求验证导入时间晚于推荐，且推荐文件的哈希与 ledger 一致。

**开发模式的限制**

- 开发模式下，`seal-dev` 从已经覆盖全部 480 个观测的历史探针里截出并集。这只演练了流程，不能证明“当时没看过未选中的输出”。
- 验证集是已揭晓的 holdout。

**预算（逻辑预算与实际离线成本分开计）**

| | 每观测 | 每策略（120） | 四策略逻辑合计 | 实际并集（共用计算） |
|---|---|---|---|---|
| 前瞻草稿：NFE {1,2,3,10} × 2 噪声 | 8 次块预测，32 次速度场求值，其中 NFE10 参考占 20 次（62.5%） | 3840 次速度场求值 | 480 个观测，15360 次 | **248 个观测，7936 次**（为逻辑合计的 52%） |
| 开发：Pi {1,2,10} / Smol {1,2,3,10} | Pi 26 次 / Smol 32 次 | 3120 / 3840 次 | 480 个观测 | 253 个观测，6578 / 8096 次 |

- 只有一个策略单独部署时，它的预算就是 120 个观测；共用并集是多策略对照实验的成本。
- Pi 的 GPU 时间按历史每观测 2.39 s 估算（来自 NFE {1,2,10} 的 480 帧运行，共 1148 s），并集约 590 s。加入 NFE3 会稍多，这是低估值。
- 开发探针当时实际覆盖了全部 480 个观测，属于沉没成本，不计入协议预算。

**改动**

- `probe_pi05_nfe.py`、`probe_smolvla_nfe.py` 新增可选参数 `--nfes`，默认值不变。前瞻时 Pi 由此加上 NFE3。尚未在 GPU 上冒烟测试。
- 前瞻探针请求文件已用 `load_shared` 在 CPU 上读通（248 条）。

### 6.2 最小适配（`probe_molmoact2_nfe.py`，尚未编写）

1. 用 `load_policy.py` 加载模型，保持 eager 模式、关闭 CUDA graph，并断言推理模式解析为 continuous。
2. 每个（观测, 噪声）组合、每个 NFE 都新建 `torch.Generator(device).manual_seed(noise_seed)`，再调用 `predict_action_chunk(batch, num_steps=n, generator=g)`。这样不同 NFE 的初始噪声完全相同；同时记录噪声的哈希。
3. 保存后处理之前的输出（手臂为 QUANTILES 归一化值，夹爪为原始值）。夹爪按原始值 >0 判为“合”，但需与 Molmo 闭环的环境约定核对。
4. 正确性检查与 Pi 相同：
   - 速度场调用次数等于 n（钩子挂在 `action_expert.forward_with_context`）；
   - NFE=10 与官方路径的最大绝对差为 0；
   - 重置后重复运行结果一致。
5. 观测取自 Molmo 数据集 parquet，经 Molmo 预处理器处理。

### 6.3 冻结前提（未满足之前，Molmo 不进入冻结配置）

- **M1 探针正确性**：Molmo 探针按 6.2 第 4 条在 GPU 上通过正确性检查。
- **M2 开发输出**：在开发池 480 个观测上生成 Molmo NFE {1,2,3,10} × 2 噪声的输出。需要先下载 101 个分片，约 8.5 GB。这属于新的开发输出，需要单独授权。
- **M3 基准可用**：Molmo 的随机基准不退化（median f ≥ 1e-3），夹爪基准可计算；bf16 噪声和 bf16 求解对基准的影响要有记录。
- **M4 规则演练**：用同一条比值规则在 Molmo 开发输出上演练。规则本身与模型无关，但比值 1.0 对 Molmo 是否有意义，只能看 Molmo 自己的开发输出，不借用 Pi/Smol 的结论。
- **前瞻数据**：前瞻所需的 Molmo 分片还要另外下载约 21 GB（§3）。

## 8. 冻结前需要决定的事项

1. **比值 1.0 是否接受。** 开发数据显示它对 Pi 偏保守（闭环可接受的 NFE=1 被拒）。备选：
   - 更严：改用上置信界 ≤ 1；
   - 更松：改用比值 1.25 之类的常数。

   只能在冻结前选定，选定后不再改。
2. **严重夹爪检查。** 开发数据里从未触发，保留作安全检查还是删除。
3. **数据划分。** 采用校准 10 + 验证 4 / 任务（当前草案），还是校准 12 + 验证 2。
4. **套件下降 5 pp。** 这是对“套件塌掉”的新量化，需要审批。
5. **候选集合。** 是否在 {1,2,3} 之外加 5，作为回退 10 之前的中间档。
6. **Molmo。** 是否授权下载 101 个开发分片并生成 Molmo 开发输出（M2），以及 Molmo 的前瞻实验是否与 Pi/Smol 同批进行。
7. **GPU 冒烟测试。** 用 `--limit 2` 验证 Pi `--nfes 1,2,3,10` 和探针请求文件，需要少量 GPU 时间。
8. **适用范围。** 本协议只覆盖完整模型。剪枝模型（Drop-6 / Drop-16）的联合配置需要另跑同规则探针，建议不能从完整模型直接移植。
